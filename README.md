# 养老助餐平台 · 志愿者帮送与家属代订签收效力、责任划分

## 原始需求（本次）

增加志愿者帮送与家属代订的签收效力及责任划分。志愿者帮送时，平台先核验志愿者身份、所属社区或组织、是否经过助餐培训、当日健康状态和帮送路线，记录其与老人的关系及老人或家属是否知情同意。志愿者取餐时同样登记保温箱、出餐批次和预计送达时间，但签收方式区别于骑手：老人本人签收、家属代签、邻里见证或志愿者拍照留证需按老人认知状态和社区授权规则判定效力，不能仅凭志愿者自述完成核销。若志愿者帮送途中餐品洒漏、迟到、送错地址或老人否认收到，平台按该餐单生成异常，先由社区核实志愿者路线、取餐时间、送达照片和老人反馈，再决定补送、退餐或重新签收；涉及食品安全或老人不适的，志愿者、厨房和社区各自记录责任，不能直接归到骑手考核。家属代订时，代订人需登记与老人关系、授权方式和联系电话，代订人可代确认菜单、禁忌、补贴资格和自费金额，但老人实际用餐后的口味反馈、身体不适和签收异常仍须回访老人本人或同住人，避免代订人代替老人放弃权益。志愿者帮送和家属代订产生的补贴核销，以实际用餐人签收或社区核实结论为准；代订人自费支付的部分，账单同步家属端和老人端，退餐或补送按原餐单重新核销。志愿者累计帮送次数、异常率和老人评价进入社区志愿记录，连续异常或未经培训的暂停帮送资格；社区端可看到帮送任务和签收状态，厨房端可看到代订人和实际用餐人区分，财政端可看到每笔核销对应的真实签收依据。

> 前序模块「老人状态变更四段清算」原始需求见附录一；底座平台原始需求见附录二。

## 需求落点

### 志愿者发车前五项核验
身份核验、所属社区/组织、助餐培训（含培训日期）、当日健康打卡（健康/不适+体温）、帮送资格；任一不通过即不能取餐。取餐再登记保温箱、出餐批次、预计送达时间、与老人关系、老人/家属知情同意人。

### 四种签收方式的效力判定（区别于骑手）
| 签收方式 | 效力判定 |
| --- | --- |
| **老人本人签收** | 直接有效 |
| **家属代签** | 直接有效 |
| **邻里见证** | 老人档案需社区授权且已知情同意、登记见证人；认知障碍/独居/行动不便等严格对象一律先社区核实 |
| **志愿者拍照留证** | 一律「待社区核实」，**不能仅凭志愿者自述核销** |

待核实签收餐单置为 `verify_pending`，社区回访老人本人/同住人核实后才转为有效并纳入补贴；否认收到则转异常退餐。

### 帮送异常与三方责任
餐品洒漏/迟到/送错地址/老人否认收到生成「志愿者帮送异常」；社区核实路线、取餐时间、送达照片、老人反馈后决定**补送/退餐/重新签收/无责**，并在**志愿者/厨房/社区**之间划分责任（食品安全或老人不适分别留痕），**不计骑手考核**；志愿者连续 2 次担责或未完成培训自动暂停帮送资格。

### 家属代订授权与本人回访
代订人登记与老人关系、授权方式、联系电话；可代确认菜单/禁忌/补贴/自费，但口味反馈、身体不适、签收异常须回访**老人本人或同住人**，代订人不能代老人放弃权益。订单区分「代订人」与「实际用餐人」，自费账单同步家属端与老人端，退餐/补送按原餐单重新核销。

### 核销真实依据
每笔补贴核销以**实际用餐人签收或社区核实结论**为准，财政核销明细逐单显示签收依据（本人/家属代签/邻里见证已核实/拍照已核实/社区核实）；待核实、核实无效、退餐、暂停单均不发放补贴。

# 前序模块：老人状态变更（住院/转院/搬离/去世）四段清算

## 需求落点（四段清算口径）

| 事件 | 已签收 | 在途（骑手已取餐） | 已备餐未出餐 | 未备餐 |
| --- | --- | --- | --- | --- |
| **住院/转院暂停** | 记录保留，补贴正常结算 | 停止配送携回，补贴**冻结**暂不核销 | 暂停保留，记批次/数量/成本，可转配 | 取消，释放补贴额度 |
| **搬离·超出覆盖范围** | 保留，按已用清算补贴 | 携回，自付退餐、补贴不核销，回收保温箱 | **按退餐处理**，记批次/成本可转配 | 停止后续配送并取消 |
| **搬离·仍在覆盖范围** | 正常履约 | 按新地址继续配送 | 正常出餐（仅改地址） | 正常备餐（仅改地址） |
| **老人去世** | **保留已签收记录**，补贴正常结算 | 停止配送，**记食材损耗+厨房责任**，可转配 | **不进财政结算**，记食材损耗+厨房责任，可转配 | 取消，停止核销 |

- **登记要素**：生效日期、经办人、家属确认人；住院/转院额外登记医院、预计出院日、家属联系人、补贴资格是否保留。
- **先结异常再清算**：存在未办结的补送/改约/退餐/回访工单时，系统拦截，必须先按原异常餐单结清。
- **出院恢复**：重新核验送餐地址、饮食禁忌、补贴资格、紧急联系人；暂停期间挂起餐单一律退餐且不核销；按实际签收含补贴餐单重算**当月剩余可享次数**，防止暂停期间被重复核销。
- **责任与转配**：已按批次出餐、食材已消耗或骑手已取餐的，不按未服务核销；记录批次号、份数、食材成本、厨房责任，并可转配给其他在服老人。
- **多方同步**：家属端、社区端、厨房端、财政核销端、骑手端均收到站内通知。


## 技术栈

- **前端**：Vue 3 + Vite + Element Plus（构建后由后端统一托管，单容器交付）
- **后端**：Go 1.25（Gin + pgx + JWT + bcrypt）
- **数据库**：PostgreSQL 16（仅 compose 内部网络，不对外发布端口）

## 一键部署（Docker）

```bash
cp .env.example .env        # 按需修改端口与密钥
docker compose up -d        # 构建并启动 app + db
docker compose ps           # 等待 app 变为 healthy
```

- 应用访问地址：`http://localhost:${CC_PUBLISH_PORT}`（默认 3079，`.env` 中 `CC_PUBLISH_PORT` 可改）
- 仅应用服务发布到宿主端口；PostgreSQL 只在 compose 内部网络供 app 访问
- 首次启动自动完成建表与演示数据初始化（种子数据中的餐单日期相对启动当天生成，任何一天部署都可完整演示）
- 停止并释放：`docker compose down`（加 `-v` 可同时清空数据）

## 推荐演示路径（关键业务流）

1. **订餐**：`family01` 登录 → 订餐下单 → 为张秀英选餐（可见饮食禁忌、补贴实时试算、严格签收标记）
2. **厨房**：`kitchen01` → 厨房工作台 → 创建今日批次 → 录入实际出餐数量（可故意少做 1 份体验「厨房少做」异常）→ 完成出餐
3. **配送**：`rider01` → 配送任务 → 接单 → 取餐（保温箱编号）→ 送达签收（张秀英为严格签收对象：必须上传照片+敲门确认+签收人）；可改试「异常上报（老人未开门）」
4. **社区**：`community01` → 异常工单 → 电话/上门回访（记录老人状态）→ 办结（关闭/重新配送/退餐退款）；餐盒回收台账登记回收或催回
5. **现场取餐**：`community01` → 餐单详情 → 社区食堂自取单 → 现场签收并回收餐盒
6. **补贴资格变更**：`community01` → 老人档案 → 补贴资格变更 → 在途餐单自动重算并通知财政
7. **未开门安全回访**：`rider01` 配送任务可见张秀英「重点关注/电话确认」提示 → 异常上报选「老人未开门」须勾选敲门+电话等联系记录 → 连续 2 次后 `community01` 异常工单可「上门查看」→ 回访登记老人状态并调整后续配送方式（电话确认后再上门），风险标签与次日重点关注联动更新
8. **餐盒押金**：`community01` → 餐盒回收 → 对超阈值老人「收取押金」（困难 10 元/普通 20 元）→ 困难老人「申请免押」指定志愿者 → `admin` 审批 → `volunteer01` 志愿回收登记（库存实时更新）；普通老人由家属/社区「缴纳押金」→ 社区「上门回收」→「退还押金」
9. **财政核销**：`finance01` → 财政核销 → 生成当月核销单（实际签收才计入补贴，退餐/异常/回收率/厨房结算一并汇总；暂停挂起单标注「补贴冻结不核销」）→ 确认 → 归档财政档案（餐单转为「已核销」，档案锁定）
10. **住院暂停四段清算**：`community01` → 侧边「状态变更清算」→ 可见孙桂英住院单 → 进入详情查看四段（已签收/在途/已备餐未出餐/未备餐）各自的批次、份数、成本与处理方式，以及冻结补贴、食材损耗、厨房责任标记；点「出院恢复 / 重新核验」→ 填送餐地址、饮食禁忌、补贴资格、紧急联系人、家属确认人 → 确认后暂停挂起餐单一律退餐且不核销，并显示重算的当月剩余可享次数
11. **现场登记一次住院**：`community01` → 状态变更清算 → 登记 → 选在服老人（如李建国）→ 住院暂停 → 填医院/预计出院日/家属联系人/补贴是否保留/家属确认人 → 下一步预览四段（若有未办结异常会被拦截，要求先结清）→ 确认执行；随后该老人下单会被「住院暂停」拦截
12. **搬离覆盖判定**：登记搬离，新地址含「幸福里/康乐/朝阳社区」等辖区关键词判定为**仍在覆盖区**（仅更新地址、继续服务）；填区外地址（如「临江市滨湖花园」）则**停止配送、退餐、回收餐盒保温箱、清算补贴**
13. **去世清算**：登记去世 → 已签收保留并正常结算、未出餐不进财政结算、骑手已取餐/已出餐未送达记食材损耗与厨房责任；厨房/社区可在详情页把已备餐食**转配**给其他在服老人，社区/骑手登记餐盒保温箱回收
14. **多方同步**：每次状态变更后，分别用 `family01`（家属端）、`community01`（社区端）、`kitchen01`（厨房端）、`rider01`（骑手端）、`finance01`（财政核销端）登录，铃铛通知与餐单状态一致
15. **志愿者发车核验**：`volunteer02`（未培训/暂停）→ 配送任务取餐被拦截；`volunteer01` 先做当日健康打卡 → 发车核验全绿才能取餐
16. **志愿者四方式签收**：`kitchen01` 为志愿者单建批次出餐 → `volunteer01` 取餐（登记保温箱/批次/ETA/与老人关系/知情同意人）→ 签收分别试「本人/家属代签」（立即有效）、「邻里见证」（需授权+知情）、「拍照留证」（自动转 `verify_pending` 待核实，不核销）
17. **社区核实签收**：`community01` → 异常工单中找到拍照留证待核实单 → 餐单详情「回访老人本人/核实签收」（本人/同住人确认收到、口味、是否不适）→ 有效则转已签收并纳入核销；否认收到则转异常
18. **帮送异常责任划分**：异常工单 → 志愿者帮送异常「餐品洒漏」→ 社区核实（路线/取餐/照片/老人反馈）→ 选补送/退餐/重新签收 + 责任划到志愿者/厨房/社区（勾选食品安全/老人不适），不计骑手；志愿者连续 2 次担责自动暂停资格（在「志愿者资质考核」页查看帮送次数/异常率/评价）
19. **家属代订授权**：`family01` 订餐时填与老人关系、授权方式、电话；订单详情区分代订人张强与实际用餐人张秀英；`community01` 对家属代订单「回访老人本人」，口味/不适只能由本人或同住人确认
20. **财政核销看真实依据**：`finance01` 生成当月核销单 → 明细列展示每笔「真实签收依据」，拍照待核实/核实无效/退餐/暂停均不发放补贴，仅实际用餐人签收或社区核实结论计入

## 核心设计

- **同一餐单协同**：餐单详情聚合老人档案快照、菜品明细、补贴金额、厨房批次、配送（保温箱/路线/照片/签收）、异常工单、回访记录、餐盒台账、用餐反馈与状态时间线，家属端/社区端/厨房端看到的状态实时一致
- **严格签收**：认知障碍/独居/行动不便老人的餐单自动标记严格模式——送达必须照片+敲门确认+签收人，异常工单自动升为高优先级
- **未开门安全回访**：骑手未开门上报强制记录敲门/电话/邻里询问/家属联系四步；连续未开门计数超阈值（≥2 次）后社区可发起上门查看；回访结果联动老人风险标签（正常/关注/高风险）、次日重点关注与后续配送方式（可改为电话确认后再上门）；未开门事件实时同步家属与社区网格员，骑手端任务列表提前展示重点关注与未开门风险提示
- **餐盒回收押金**：连续未归还（≥3 个）记录未回收数量/提醒次数/家属反馈并可收取押金；押金规则按老人类型区分（普通 20 元、困难 10 元）；困难老人可由社区负责人申请免押并指定回收志愿者，管理员审批留痕（申请人/审批人/志愿者责任链，防止餐盒责任空转）；社区可选择上门回收、改用一次性餐盒或暂停新增发放；回收（含志愿回收）实时更新餐盒库存
- **异常联动**：未开门、餐盒未回收、家属临时改餐、厨房少做、骑手超时、补贴资格变更、饭菜不适合七类异常统一进入工单，触发社区回访，并与补贴核销联动（未签收/退餐不发放补贴）
- **补贴核销**：月度核销逐单判定发放依据，汇总实际签收、补贴金额、退餐、异常回访、餐盒回收率、厨房结算，归档后锁定为财政档案
- **状态变更四段清算**：住院/转院/搬离/去世以生效日期将在服餐单拆成四段并分别处置；住院登记医院/预计出院日/家属联系人/补贴是否保留；出院恢复重新核验四要素、结清暂停餐单（退餐不核销）、重算当月剩余次数；搬离按覆盖范围决定继续服务或停配退餐回收；去世停配停核销、保留签收、未出餐不结算、已出餐未送达记食材损耗与厨房责任；已备餐批次/数量/成本留痕并可转配；未办结异常先拦截结清；全程记录生效日期/经办人/家属确认并同步五端。数据表 `elder_status_changes`、`status_change_items`，餐单新增 `paused` 状态与 `subsidy_frozen` 标记，老人新增 `service_status`、`monthly_quota`，菜品新增 `unit_cost`。
- **志愿者帮送签收效力（本次新增）**：`users` 增加志愿者资质（组织/身份核验/培训/资格），`volunteer_health` 记录当日健康；取餐强制发车五项核验与知情同意；签收四方式按认知状态+社区授权判定效力，邻里见证/拍照留证转 `verify_pending` 待社区核实，绝不仅凭志愿者自述核销；帮送异常（`volunteer_delivery`）记录责任方（志愿者/厨房/社区，非骑手）、食品安全、老人不适、核实结论；连续 2 次担责或未培训自动暂停资格。数据表 `elder_confirmations` 记录老人本人/同住人回访；餐单新增 `proxy_*` 代订授权、`sign_basis/sign_effectiveness` 签收依据；核销明细带真实签收依据。
- **家属代订授权**：代订登记关系/授权方式/电话，订单区分代订人与实际用餐人，自费账单同步两端；口味、不适、签收异常必须回访老人本人或同住人。

## 附录一：前序模块原始需求（四段清算）

老人住院、转院、搬离服务区域或去世时，餐单按生效日期拆成已签收、在途、已备餐未出餐、未备餐四段。住院暂停要登记医院、预计出院日、家属联系人和补贴资格是否保留；出院恢复时重新核验送餐地址、饮食禁忌、补贴资格和紧急联系人，并重算当月剩余可享次数，避免暂停期间被重复核销。搬离时先判断新地址是否在覆盖范围内，超出范围就停止后续配送、回收餐盒和保温箱，按已用与未用清算补贴；已备餐未送出的按退餐处理。老人去世时停止配送和补贴核销，保留已签收记录，未出餐部分不进财政结算，已出餐未送达的记食材损耗和厨房责任。厨房已按批次出餐、食材已消耗或骑手已取餐的，不能按未服务直接核销，要记已备餐批次、数量、成本和可否转配给其他老人。暂停或终止前如果还有补送、改约、退餐、回访没处理完，先按原异常餐单结清，再进入清算。状态变更要记生效日期、经办人、家属确认，并同步家属端、社区端、厨房端和财政核销端。

## 附录二：底座平台原始需求

建设养老助餐配送餐盒回收与补贴核销平台，可采用 Vue 3、Go 和 PostgreSQL。老人、家属或社区工作人员提交订餐时，平台记录老人身份、补贴资格、饮食禁忌、送餐地址、是否需要敲门确认、餐盒回收方式和紧急联系人。厨房按菜单、营养要求、低盐低糖、软烂程度和出餐批次备餐；骑手取餐后记录保温箱、路线、送达照片、老人签收和是否发现异常。若老人未开门、餐盒未回收、家属临时改餐、厨房少做、骑手超时、补贴资格变更或老人反馈饭菜不适合，平台要把老人、家属、社区、厨房、骑手和财政核销放在同一餐单里处理。月底核销时，实际签收、补贴金额、退餐、异常回访、餐盒回收率和厨房结算进入财政档案，防止补贴发放和实际服务脱节。平台还要处理老人不会使用手机、家属代订、社区食堂现场取餐、特殊节日加餐和志愿者帮送。助餐服务既涉及财政补贴，也涉及老人安全，配送异常需要触发社区回访和补贴核销联动。家属端、社区端和厨房端看到的餐单状态需要一致；当老人有认知障碍、独居或行动不便时，签收照片、敲门确认和异常上报要比普通订单更严格。
